# Financial Planning App — Project Scope (v1: Foundational Five)

## The idea
A financial planning app that takes complex-feeling financial decisions and makes them
genuinely understandable — not dumbed down, just well-organized — while still giving
users every option and every number they'd need. Long-term wedge is decoding complex
instruments (RSUs, options, alternatives) that nobody explains well. **v1 scope is
deliberately narrower**: nail retirement + index investing basics first.

Secondary goal: building this is also how you (Ethan) learn the material. Each account
type gets a "learning log" entry written in your own words before that feature gets built —
that log becomes the actual source content for the app's explanations.

## Who it's for
Real product, general users — people who know they should be saving/investing but find
the account landscape (401k vs IRA vs Roth vs HSA vs taxable) confusing enough that they
under-optimize or freeze.

## Interaction model
Two surfaces sharing one source of truth:
- **Dashboard** — persistent state: accounts, balances, a prioritized action list.
- **Chat** — reasoning layer on top of the same state; answers are grounded in the
  user's actual numbers, not generic advice. Can write actions back to the dashboard.

## Legal/positioning note
Framing this as **educational/informational**, not "we tell you what to buy," keeps you
out of investment-adviser registration territory (SEC/state RIA rules kick in around
giving personalized buy/sell advice for compensation). Explain the well-established
prioritization waterfall and the mechanics of each account type; don't direct specific
trades or take custody of money. Revisit this if you plan to charge AUM-based fees.

## v1 Account Types ("Foundational Five")

1. **401(k)** — traditional vs. Roth, employer match, contribution limits
2. **IRA / Roth IRA** — eligibility, income phase-outs, backdoor Roth basics
3. **HSA** — triple tax advantage, often-skipped but arguably the best account type
4. **Taxable brokerage** — for after tax-advantaged space is used
5. **Index funds / target-date funds** — the vehicle inside the above accounts

## Current numbers to build against (2026, per IRS Notice 2025-67 / Rev. Proc. 2025-19)

| Account | 2026 Limit | Catch-up (50+) | Notes |
|---|---|---|---|
| 401(k) employee deferral | $24,500 | +$8,000 (ages 50-59); +$11,250 (ages 60-63) | New for 2026: catch-ups mandatory Roth if prior-year wages from that employer > $150,000 |
| IRA (Trad + Roth combined) | $7,500 | +$1,100 | Roth phase-out: $153,000–$168,000 MAGI (single); $242,000–$252,000 (MFJ) |
| HSA — self-only | $4,400 | +$1,000 (age 55+) | Requires HDHP enrollment |
| HSA — family | $8,750 | +$1,000 (age 55+) | |

(These change annually — treat this table as seed data, not hardcoded constants, so next
year's update is a data change, not a code change.)

## Prioritization waterfall (the recommendation engine's core logic — deterministic, not AI-guessed)

1. Emergency fund (3–6 months expenses) before investing at all
2. Capture full employer 401(k) match (instant guaranteed return)
3. Pay down high-interest debt (generally >7-8%)
4. Max HSA (if HDHP-eligible) — triple tax advantage
5. Max Roth or Traditional IRA (Roth generally preferred if in lower bracket now than expected in retirement)
6. Max remaining 401(k) space
7. Taxable brokerage investing

This logic is intentionally rules-based and inspectable — every recommendation should be
traceable to a specific rule, not a black-box output. Keeps it honest and legally cleaner.

## Layered disclosure pattern (applies to every account/instrument page)

- **Layer 1 — Decision:** one-line "here's what this means for you" statement
- **Layer 2 — Why:** plain-English mechanics, one paragraph
- **Layer 3 — Full detail:** exact numbers, limits, edge cases, scenario comparisons

## Data model (rough v1)

- `User` — age, income, filing status, state
- `Account` — type (401k/IRA/HSA/taxable/brokerage), balance, contributions_ytd, employer_match_rate (401k only), roth_or_traditional
- `Goal` — emergency_fund_target, retirement_target, timeline
- `ActionItem` — generated by the waterfall engine, links to the rule that produced it, status (done/pending)
- `LearningLog` — per account type, your own-words explanation (source content for Layer 2/3 copy)

## Suggested stack (matches your usual approach) — kept fully free, no paid APIs
- Frontend: React + Vite + Tailwind
- Backend: Flask — owns the waterfall logic and account data (deterministic, not LLM-driven)
- "Chat" layer, v1: structured Q&A / decision-tree UI built from the Layer 1/2/3 content
  for each account type — no external API, no cost, fully deterministic (also keeps the
  legal framing clean — no AI-generated financial explanations to vet)
- Deploy: Vercel (frontend) — confirm Flask hosting target separately, Vercel's Python support is limited for stateful backends

### Decisions made building the bot
- **No LLM, on purpose, twice over.** There are no API credits, and a model that
  composes answers can compose a contribution limit that doesn't exist. The bot
  *selects* — a canned personal answer, a written knowledge entry, a decline, a glossary
  definition — or *parameterises* the engine. It never writes a number.
- **The depth bar is one question:** "How should I plan around my 35K of student debt?"
  It can't be retrieved, because the answer depends on a number typed at runtime. So a
  second subsystem reads the sentence's slots, runs them as a what-if on a deep copy
  (the same discipline as `/api/target`), and composes the answer from engine output.
- **Cadence separates a stock from a flow.** "$300 a month" moves; "35k of debt" sits.
  That one tell is what routes a sentence to the right scenario.
- **The assumed rate is disclosed, not buried.** An unstated interest rate is the hinge
  of the whole debt answer — 6.5% sits below the 7.5% line, 8% flips it — so composed
  answers carry an `assumptions` block the UI renders visibly, and the break-even rate
  is part of the answer.
- **Both routes deploy the same cash.** The first version of the payoff-versus-invest
  comparison let the investing route keep making minimum payments for free, which made
  a 22% card look worth keeping. The simulation now gives both routes identical money
  each month and differs only in order; the 22% card correctly shows ~$49k in favour of
  paying it off, and a 6.5% loan shows a near coin-flip.
- **No new write endpoint.** A scenario's `save_hint` names the existing endpoint and
  body; "Save this to my plan" just calls it. The write path and its tests stay put.
- **Intent without a number asks.** "How should I handle my student debt" with no
  amount returns `needs_input` and asks for the balance rather than inventing one.
- **Confidence is part of the contract.** Every result carries a 0–1 figure; below
  0.55 the UI shows "did you mean", below 0.25 a browse list. A bare glossary word gets
  its definition; a bare common word gets choices; gibberish that typo-repairs into a
  real word is caught by counting the words that couldn't be placed.
- **Context is client-carried.** The response echoes `{previous_id, previous_topic,
  previous_entity, previous_related}`; the client sends it back. A follow-up is only
  treated as one when it's short and referential, and its natural targets become
  candidates even with zero word overlap — "what about traditional?" shares no token
  with the Roth-versus-traditional question once aliasing runs.
- **Aliases are the product.** Match quality came almost entirely from the phrase map
  and keyword lists, not the scoring. The stress corpus (`backend/tests/phrasings.py`,
  ~380 rows) went from 331 to 378 passing through alias work and four real bugs: `401k`
  parsing as $401,000, the number filter dropping the `401k` entity, the stemmer turning
  the alias token `whatis` into a content word, and a debt-scenario floor firing on any
  mention of debt when a debt was on file.
- **The knowledge base is not the learning log.** ~85 reference entries were written to
  ship the breadth; `LEARNING_LOGS` stays in Ethan's own words. The README says so.

### Decisions made making the plan customizable
- Retirement age changes the *advice*, not just the chart. Before 59½ the plan sizes
  "bridge" money you can reach without a penalty and slots it after the IRA, ahead of
  extra 401(k) space; before 65 it flags the health-coverage gap; past the RMD age it
  flags required withdrawals.
- Readiness never picks the fix. Short plans get all three levers with numbers — extra
  saving per year, the earliest age the current plan supports, and the spending that
  lasts — each tryable in place on the projection page.
- Everything compares in today's money, and the money has to last to 95 by default:
  running out at 88 is the failure that matters, not missing average life expectancy.
- Unknown Social Security counts as zero, and the copy says so, rather than guessing.
- What-ifs run on a copy of the profile via query params; nothing saves until the user
  presses "Save as my plan".

### Decisions made building the schedule
- A plan people follow is a *date and an amount*, so every move carries both its monthly
  figure and its per-paycheck one, and payroll lines are expressed as a percent of pay —
  that's the box you actually fill in at work.
- Payroll money is paced across the remaining months rather than front-loaded. Filling
  the 401(k) limit by June can forfeit match for the rest of the year in a plan without a
  true-up, so "as fast as possible" is the wrong default for deferrals only.
- Minimum debt payments are treated as bills inside monthly expenses, not as savings.
  Balances still move by interest minus the minimum each month, so the payoff month in
  the twelve-month table is real rather than optimistic.
- Deferrals aren't subtracted from take-home pay in the payday breakdown — they never
  reach the account. Subtracting them would double-count and make the plan look
  unaffordable.
- Savings capacity is now entered per month (stored as the same annual field). "What can
  I save this year" is a harder question to answer honestly than "what can I save this
  month".

### Decisions made building the estimator

- One stored number, many units. `annual_savings_capacity` stays the only figure the
  rules read; `savings_basis` + `savings_amount` record what the user typed. Deriving
  the first from the other two on every write means they can't disagree, and a
  percent-of-pay plan follows a raise instead of quietly going stale.
- A percentage is the version that travels. "15% of pay" means the same thing on any
  salary and rises with it by itself, which is why it's offered alongside dollars rather
  than being treated as the advanced option.
- The estimator never writes. A target is a question, so `/api/target` runs on a copy —
  the same discipline as the projection's what-ifs.
- Required contributions are quoted in every unit at once rather than making the user
  divide. Which one lands is personal: per-paycheck for a standing transfer, percent of
  pay for a payroll box, monthly for a budget.
- The coast number is reported as prominently as the target. "You could stop at
  $275,000" is a truer picture of the task than the seven-figure number, and it arrives
  years earlier.
- When the answer is impossible, say so instead of quoting a number. More than you earn
  gets its own note, and it suppresses the lesser ones — where the overflow would land
  is noise when the target can't be reached at all.

### Decisions made building the Q&A layer and projections
- The demo seed is a 20-year-old student on part-time minimum wage rather than a high
  earner. It exercises the low-income branches, and it makes the projection's case
  honestly: $54,450 paid in becomes ~$354,000 by 67, almost all of it growth.
- That persona surfaced a real correctness gap: **IRA contributions are capped at earned
  income**. Never binding at $118k, always binding for a student. Now enforced in
  `limits.ira_limit`, and the copy explains the cap rather than just quoting a number.
- It also surfaced a silent step: with no 401(k) at work, rule 2 emitted nothing. It now
  returns an `info` item explaining why the step doesn't apply.
- Projections model debt payoff and emergency-fund saving as a *delay* before investing
  starts, not a recurring annual cost — the naive version projected "$0 a year, forever".
- Three return scenarios, never one, and the assumptions render expanded by default.
- Behaviour tests moved onto a `rich_client` fixture so the seed profile is demo copy,
  not a test fixture, and can change without breaking the suite.

### Decisions made during the frontend build
- Palette is white + green with contrast measured per token, solved against the darkest
  surface each colour lands on rather than against white. Zero axe WCAG A/AA violations.
- Added a `GLOSSARY` to `content.py` (and `GET /api/glossary`): the target audience is
  specifically people who freeze at this vocabulary, so every term the UI can't avoid
  using is tappable for a plain-English definition.
- The action list is re-sorted by `(priority, step)` for display. Waterfall order put a
  card badged "Do this first" in third place, which reads as a contradiction.
- Action cards say "#N on your list", not "Step N" — the rule copy already uses "step"
  for waterfall position and the two numberings diverge once sorted by urgency.
- The plan header leads with the single next action; the progress bar is secondary, so a
  new user isn't greeted by "0%".

### Decisions made during the backend build
- Added `Debt` to the data model — rule 3 of the waterfall can't be evaluated without it.
- Added `User.annual_savings_capacity`; when set, `GET /api/plan` allocates it down the
  waterfall. When unset, each step just reports remaining room.
- Allocation order is `(priority, step)`, not step alone: an emergency fund already past the
  3-month floor is a top-up, and shouldn't outrank a guaranteed employer match.
- Action items are recomputed from state every request rather than persisted. "Done" is a
  statement about the underlying numbers, which keeps the dashboard from ever showing a
  recommendation that the user's data no longer supports.
- Every rule emits something on every run — a rule that doesn't apply returns an `info` item
  explaining why, so the dashboard has no silent gaps.
